# 普通目标评审冻结（review-freeze）

> 状态：已拍板并落地（2026-09-09；2026-09-10 补齐不可变版本、返修与接受状态约束）。前身草案 `docs/review-freeze-design.md`
> 已并入本文件。对应审计 `docs/audits/architecture-audit-2026-09-09.md` §4.2。
> 改动普通目标（free_research / office_doc）的开工、收尾、评审或采纳前必读。

## 适用范围与边界

- 只覆盖普通目标链路：`task_prepare_run` / `task_output_changes` / `task_adopt_outputs`。
- 科研 worktree 评审与编程 lane 走 Git，不在本机制内；定时巡检沿用 `watch_review.rs`
  基线文件 + 技能产出契约冻结（两套机制同构，不合并实现）。
- 有冻结证据即可审，失败/停止的部分成果也可采纳；无冻结证据的旧 Run 仍要求 completed。
- 目标已接受后，Run 退出不得把目标改回待验收/失败/停止；只有用户显式返修才重新进入 running。

## 机制

```
开工（task_prepare_run_impl，Run 登记后）
  → 首次 write_baseline：记录副本与项目根的 stat 签名，小文件另记内容哈希。
    返修 continue_baseline：继承原始基线，保留上一版未修改、但尚未采纳的成果；
    不把上一版成果重新当成输入。上一版缺基线时拒绝安全续改，旧副本保留。
    写失败 = 开工失败（fail-closed），Run 记 failed，不静默降级。

收尾（close_run_with_result，账本提交后）
  → freeze_task_run_evidence：仅「review_required 的 free_research/office_doc」参与；
    对原始基线现算变更，同一次读取的字节用于哈希与副本，发布到独立版本目录；
    完整清单与副本落盘后，再原子更新当前 snapshot.json。
    无基线（旧 Run）跳过不伪造；冻结失败记 logbuf + task.snapshot_failed 事件，
    不反向影响收尾。

评审（task_output_changes → TaskReviewDto）
  → frozen=true：变更清单读 snapshot.json，预览从 payloadDir 读字节。
  → frozen=false（旧 Run / 冻结失败）：目录现算，前端弹层顶部明示「没有冻结证据」。

采纳（task_adopt_outputs）
  → 冻结路径：check_adoption 逐文件三向判定——
      项目现读 == 冻结内容        → 跳过（幂等）
      项目现读 == 开工基线        → 允许写入
      项目现读 == 本目标此前接受的内容哈希 → 允许返修写入（不是拿现读内容重设基线）
      否则                        → 整批拒绝并点名「任务开始后已被修改」
    附带：payload 实际哈希必须等于快照记录（防证据目录被外部改动）；
    写入源只认这版 payload；新冻结结果的采纳必须回传 expectSeq。
    项目采纳锁覆盖三向检查、文件应用与接受记录；文件先私有暂存再替换，
    当前文件写后报错也参与回滚，外部再次修改的文件不强制回滚。
  → 未冻结路径：有基线的新 Run 禁止实时采纳，须先重冻；无基线旧 Run 才保留现读兼容，前端明示。
```

## 验收弹层加载与稳定性

- 普通目标验收弹层使用受视口约束的固定外框，正文独立滚动；首次清单、保护路径与工作环境读取完毕后一起展示，加载与错误态不改变外框尺寸。
- 打开期间固定本次读取的结果版本。目标列表轮询返回同一 Run 的新对象，不触发验收重载，不替换文件勾选、意见或预览副本；关闭重开才读取当前版本。明确的大文件重冻与接受恢复仍走各自操作。
- 接受始终携带本次所审 `expectSeq`，后台已有新版时仍由后端拒绝旧版接受，不能用静默刷新替人确认；读取失败不得显示为空成果并允许完成。

## 存储

`task-runs/<task-id>/review/<run-id>/` 保存 `baseline.json` 与当前 `snapshot.json`；
每个新版本独立保存为 `versions/<payloadId>/snapshot.json` + `payload/`。
冻结发布持文件锁与上下文锁；只有内容变化才递增 seq，空回合/保存未改不制造新版本。新回合不删除或复用旧副本，已打开的预览仍指向原版本。
失败只清理本次未发布的目录，不能损坏旧快照。旧格式没有 payloadId 时仍读原 `payload/`，不搬走旧证据。
归档目标保留这棵树；不能以再冻结为由抹掉已接受版本。容量清理是显式两步、各需单独确认：先释放工作副本，需要时再删除历史冻结版本与写回前备份。清理后目标和接受账本保留，但不能从已删副本或旧会话续跑，只能从当前项目重新开始。中途失败保留恢复单与「继续清理」入口。不得删除仍被其他项目或运行引用的目录；中断后若待删目录被外部修改或替换，拒绝继续删除并保留原清理记录。

另有 `context.json`（2026-09-09，审计 §4.8）：开工一刻**实际下发给 Agent 的上下文全文**
（前端拼装的 Context Pack + 目标行经 `task_prepare_run` 的 `contextText` 传入，sha256 校验，
读取时哈希对不上即拒绝）。开工写失败 = 开工失败，与基线同一 fail-closed 口径。
2026-09-11：普通目标快照增加 environment + 整体摘要：本次隔离文件清单（小文件哈希/大文件 stat）、
项目规则参考、项目 ID/两处路径、Agent/权限、输入输出范围、知识摘要、点名技能完整库摘要/Agent 副本摘要及入口全文。
点名技能缺失、未分发或副本漂移拒绝启动；目标规则/知识读取失败不得按空数据继续。规则参考与 CLI 实际有效规则须区分，
不能宣称保存了父目录规则、CLI 内置指令、模型内部状态或外部工具状态，也不能从技能可用推断 Agent 实际用过。
同一 Run 继续返修把新上下文写 `contexts/<id>/context.json`，`current-context.json` 只作指针；
成果快照带 contextId，评审读成果绑定的上下文，不读下一轮最新上下文。原 context.json 与各次历史不改写。
快照文本最多 2 MB、含环境清单最多 16 MB，单个规则文件最多 512 KB；超限明确失败。
评审弹层「本次工作环境」折叠区展示（出站副本脱敏）；科研流水线仍以 TASK.md 为凭证，不为统一名字复制所有入口。

容量口径：默认单文件 > 64 MB 记 `too_large`，UI 禁选/禁预览不存在的副本，不能只等采纳报错；默认总预算 512 MB。
人明确确认「冻结大文件」后，该 Run 可用单文件 1 GB / 每版合计 4 GB 的有界预算（保存在 freeze-policy.json）。
扩展仍必须绑定所审 seq，尚未成功发布快照时以 0 为前提；失败不改旧版，不自动写项目。文件 >1 GB 仍需拆分/另行人工处理。
冻结与写回/备份使用流式文件处理，不把多 GB 前后副本同时读进内存；哈希与冻结文件来自同一字节流。
隔离输入仍保持 512 MB / 20,000 文件限制：启动前只读估算，超限在复制前拒绝；缩小资料范围，不用可写硬链接冒充隔离。
遍历排除 .git/.ccode/node_modules/target/常见 Python 缓存；文件上限 20,000，文件+目录遍历节点也有预算。
新 Run 有基线但冻结失败时必须阻止实时目录采纳（freezeRequired）；仅真正无基线的旧 Run 保留明示的兼容路径。

## 硬规则

- **项目写回只有一个临界区**：普通目标、科研合并、编程合并、定时采纳共用 `review_contract::apply_lock`；
  持锁完成检查、写入和接受记录，取锁失败不能无锁继续。它只协调 Mesa，不宣称能锁住外部编辑器。

- **人审的就是写入的**：预览与采纳读同一份 payload 字节；采纳前再校哈希。
- **删除永不自动写回**：`deleted` 只是证据行（前端划线展示、不可勾选），要删由人手动删。
- **mtime 不作数**：`run_artifacts` 的修改时间只用于候选发现，不作产出归属或版本判定依据。
- **冲突不自动合并**：三向判定不通过 = 拒绝 + 人工，不做 three-way merge。
- 新增/修改/删除的展示分组沿用 `goal-review.ts`；保护路径检查在采纳时照旧先跑。

## 接受记录（2026-09-09，审计 §4.5）

### 中断恢复合同（2026-09-11 可靠性收口）

- 普通目标第一次写入项目前，必须保存 `review/<run>/apply-pending.json`；内容包括操作 UUID、原结果版本、
  所选路径与前后哈希、备份与固定副本位置、用户意见、是否沉淀知识。备份先落盘，失败不得开始写入。
- 阶段为 prepared → files_applied → recorded → 清除恢复单。prepared 表示尚未写或部分写入；
  重开时逐文件对照前态/后态，原文件仍是前态才写，已经是后态则跳过，第三种内容拒绝覆盖。
- 用户可选「恢复原文件」，只在尚未写接受账本时允许；恢复前全批检查备份与外部变化，先持久标记 rolling_back。
  恢复中断只能继续恢复，不能改走接受；后来被用户改过的文件不强制回滚。恢复单最终删除才算结束。
- 文件阶段已确认或账本已有原事实时，重试只补账本/知识/状态，不重写文件；目标更新和 Run 事件在同一 SQLite 事务。
  项目摘要失败也保留恢复单。接受账本尾行写到一半时，下一次追加先补分行，保留原损坏字节，不把新事实拼进坏 JSON。
- 项目列表通过持久恢复单派生 `pendingApplyRunId`，哪怕目标已标完成或出现较新 Run，仍从「处理未完成接受」
  找回原操作。未处理恢复单前不得另启返修或归档；评审只显示原选择与原版本，不以最新目录重建决定。
- 恢复操作本身是显式用户动作；项目锁只协调 Mesa，外部编辑器仍需乐观比对。机器断电/文件系统损坏不是可保证的数据库级跨文件事务。


- 采纳写文件成功后，先写**长期账本** `.ccode/acceptance-log.jsonl`（append-only，普通目标按
  目标 + Run + 结果版本 + 所选路径集合 + 意见去重；选择顺序不制造重复，新版本/补采纳不得被吞掉）；账本落盘失败 = 采纳返回可见错误引导重试（已写入文件自动跳过），不许静默成功。
- `project-status.json` 是账本的「最近摘要」投影（按名替换、留 20 条）；摘要写入失败保留恢复单并返回错误，
  再次继续只补状态，不重新写项目文件。
- 接受事实记录本次所选文件的完整内容哈希；后续返修只允许覆盖仍等于这些已接受内容的项目文件，
  用户或别的目标后来修改了文件仍拒绝覆盖。旧记录没有内容哈希时不猜测前态。
- 删除即归档，不清 Run/事件/隔离目录/评审证据、摘要或账本：`task_list` 默认不含归档行；目标页「已归档」可恢复。归档确认必须写明归档不等于清理、副本仍占磁盘。待验收可以归档（主列表不再提醒，可恢复再验收）；未完成接受或未完成副本清理不得归档，清理未完成也不得恢复。

## 状态与知识边界

- 执行状态 / 结果可审 / 目标完成三分的完整语义（§4.4）：入口侧已解绑（2026-09-09 两轮）。
  第一轮：有冻结证据即可审可采纳，失败/停止 Run 有可审成果时提升待验收。
  第二轮（实机走查驱动）：**交互式 CLI 交付后不退出进程**——回合结束（终端 attention → 已回复）
  即 `task_freeze_turn` 冻结当前成果并提升待验收 + 发 `goal-review-ready` 事件（OS 通知）；
  同一 Run 允许回合间再冻结（`freeze_or_refresh`，seq 递增，每版独立存储），
  采纳按 seq 绑定「人看过的那版」，对不上拒绝并要求重看。2026-09-11 评审 DTO 的 readiness
  由冻结/可采纳/保护路径/接受记录派生（复用 review_contract），UI 不再把活进程标成失败；Run 状态机不新增领域状态。
  收尾会复查最后一次回合后的成果；内容不变不增版。执行次数与成果版数分开展示。
- 接受账本目标页只读展示最近若干条；Context Pack 仍引用摘要/`memory.md`，不把整本账本注入开工文本。
- 项目知识仍用 `.ccode/memory.md`，只由人确认；结构化 Markdown 块记录来源版本/文件指纹、替代关系、状态和依据。
  项目设置可新增、修订/重新确认、作废、停用旧自由文本；原文/历史保留，保存前比对文档 revision，持文件锁并留备份。
  修订重新绑定原来源文件的当前小文件哈希，后续变化仍提示重确认。只将有效且来源可核对的条目按最新优先注入；
  已作废/已替代条目不注入。单文件校验最多 8 MB、一次知识校验最多 64 MB，超预算标待确认而非假装未变化。
  旧自由文本原样保留并标注未绑定证据，可由人停止带入；知识全文上限 2 MB，单条 32 KB。无 Agent 自动提议区/向量库。

## 性能口径（2026-09-09 实机修正）

基线与冻结判定用 **stat 快路径**（size + mtime 纳秒，与 git stat-dirty 同源）：stat 未变即未变，
不读文件内容。小文件（≤8 MB，「人会编辑的文本」量级）在基线里同时存内容哈希——
「保存未改/撤销编辑」stat 变内容同，不算漂移；大文件（PDF/数据）stat-only，stat 变了保守判冲突。
全量 sha256 曾把 47 个 PDF 的项目开工拖到 14 秒，不得回退到全量哈希。
