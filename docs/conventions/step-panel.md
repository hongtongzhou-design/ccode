# 约定：步骤工作面板设计规范

> 来源：2026-08 对「文献检索与筛选」步骤面板的连续实测走查（用户逐屏截图反馈）。
> 那一屏踩到的每个坑都不是它独有的——**本文是从那次走查里提炼的通则，适用于全部步骤与全部模板**。
> 新增步骤、新增模板、改动 `StepFlow` / `TaskCardsSection` / `ProjectGroup` 前必读。
>
> 与 `design-system.md` 的分工：那边管**全站视觉**（令牌、线条、字号、控件密度），
> 这边管**步骤面板的信息架构**（谁先谁后、谁该出现、话怎么说）。冲突时那边优先。

---

## 一、七条硬规则

改任何步骤面板前，逐条自查。每条后面括号里是它对应的真实事故。

### R1 顺序即语义：前提必须自成节点，排在 agent 之前

开工前提（如「确定文献来源」）**不得塞进 agent 节点的内容区**——内容区在视觉上都排在「开始」按钮之后，
用户看到的是「先出发再问路」。

- 前提 → 独立节点，`section: "main"`，排在 agent 前，未满足时它就是 `currentKey`
- agent 的附属信息（预览 TASK.md）→ 才放 agent 内容区

（事故：`asksLitSource` 块原挂 agent 内容区，「开始」渲染在它上方。）

### R2 没内容的节点不出现，但判定用「是否声明」而非「是否完成」

- 节点为空（只剩一个按钮）时**不生成**，别占流程线一格
- **判定必须用「模板有没有声明」**（`decisions.length > 0 || seeds.length > 0`），
  **不能用「用户答完没有」**——答完就消失会让流程线在眼前少一格，比空着更让人不安
- 节点被隐藏时，挂在它上面的内容必须有兜底落点（见 `hasDiscussNode`）

（事故：决策项归零后「先定几件事」只剩一个按钮，用户反馈「有点空」。）

### R3 同一事实只表达一次

一个状态在同一行/同一屏里只允许有一个视觉载体。已发生过的重复：

| 重复 | 处理 |
|---|---|
| 状态图标 `✓` + 复选框 | 删图标（复选框自带状态），只留占位保持对齐 |
| 「可选」徽标 + 「可选（不做也能跑）」分组标题 | 徽标只在主干区显示 |
| 「← 当前」标签 + cta 竖线 + cta 序号 + 最亮文字 | 删标签（已有三个信号） |
| 节点名「确定文献来源」+ 块内标签「文献从哪来」 | 删块内标签 |
| 选项 hint 小字 + 选项自身 `title` | 删小字，细节留 `title` |
| 页头一句宣传语 + 空态区同义说明 | 删页头那句 |

### R4 指着按钮说「点这个按钮」是废话

`hint` 只写按钮**没说**的信息。反例：主动作是「开始」，hint 写「点「开始」交给 AI」。
正例：hint 写「上面那些不定也行——AI 会在对话里问你」（这是按钮没说的授权信息）。

流程线的常驻小字只保留按钮无法表达的上下文（例如评审验收规则）；普通运行状态、人工事项的时机和落点不再重复写在节点下方，分别由节点顺序/状态样式、按钮 tooltip 与「怎么做 / 落点」详情表达。

### R5 孤立按钮必须自带上下文，或干脆按需出现

一个没有相邻语境的按钮，用户只会问「这是干嘛的」。二选一：

- **补一句**：说清「什么时候用它 / 用完会发生什么」。旁白不得重复旁边已经有的控件——「跟 AI 商量一下」旁边已有 TASK.md 按钮，不再跟「可选 · 结论写入 TASK.md」
- **按需出现**：让它跟随它所服务的对象（如「聊天时不让 AI 改文件」跟随已有话题出现——没聊过话题时它没有约束对象）。
  注意边界（2026-08-20 两轮实测）：「跟随对象出现」的前提是对象有别的出生口——「＋ 话题」曾只在已聊过话题时出现，
  依赖预置种子建第一张卡；无种子步骤删掉最后一个话题后入口彻底消失。但改全步骤常显又走过头：
  检索这类纯执行步骤（role≠you）零话题时多个没约束对象的入口只会添乱。**落点：想法区零态入口
  仅 role=you 的步骤常显**（人主导的步骤开放讨论最有价值），其余步骤有卡才现；role 是既有的中性字段，
  不为这件事新增配置

### R6 主路径唯一，门控只来自显式决策契约

- 每个步骤有且只有一个最显眼的主动作（`text-sm` 实心 CTA，其余控件 `text-xs`）
- **右栏只留给主动作**：步骤卡右缘只放「开始 / 去评审 / 恢复工作区」。次要动作（去补几篇、TASK.md、全部用推荐值）跟在所在行标签后面，禁止 `ml-auto` 拉到右缘与主动作上下叠在同一条槽。主干节点之间 `space-y-3`，节点标题与其下选项 `mt-1.5`。六套模板共用 `StepFlow` + 当前步骤卡外壳，改一处即全部步骤生效。
- **普通讨论/可选事项不加门控**；模板显式 `hard_pause` 的结构化决策未选「批准指定范围」时不可正式开工，「仅允许准备」需二次确认，待补／不批准／旧纯文本都不算授权。`soft_pause` 仅允许无依赖可逆准备。不得以便捷开工绕过科研问题/设计/数据授权；详情见 pipeline.md 科研质量契约。
- 可选路径必须**标上「可选」**，否则新用户会以为是必经步骤

（事故：「还有 3 件要定」看着像必办任务，实际一件不答也能开工，落差本身就是困惑源。）

### R7 步骤名保留学术术语，角色单独标

用户要知道的是**哪几步轮到我**，不是「这步产出什么文件」。

- 步骤名沿用学术习惯叫法（文献检索与筛选、综述大纲）
- `role` 字段（`ai` / `you` / `both`）单独渲染标记；**只标非默认**：「你来」「一起」出现，「AI 做」不画（流程线节点已写「AI 干活」）。**标错的后果是用户以为这步不用管**
- 流程感来自**角色交替**，不是序号

## 二、问题该在什么时刻、什么层级出现

新增决策项 / 人工事项前，先过这张表。**这是本规范最核心的一条**——
内容写得再对，摆错时间或层级一样是负担。

| 这个问题… | 归属 | 落点 |
|---|---|---|
| 决定后面**每一步**（篇幅、读者、语种、目标期刊、去向） | **项目层** | `project.toml` 的 `settings`，项目头展示，每步 TASK.md 自动带上 |
| 开工前**就能答**、答了确实影响执行（数据从哪来、敏感字段怎么处理） | **步骤决策项** | `steps[].decisions`，流程线默认折叠 |
| **要先看到数据**才定得了（纳入标准、分析粒度、算力、字数裁剪、精读力度——v3.97 实测：力度取决于清单规模与全文到位率，开工前点卡片 = 盲猜） | **按需问** | 简报里写死「先报数再问」，走 `.ccode/help-wanted.md` → 收件箱 |
| 答案不可枚举、需要来回聊，且**开工前就能聊出结论** | **讨论种子** | `steps[].discussionSeeds`，点击即聊 |
| 只有人能做（下载付费全文、放入成稿） | **人工事项** | `steps[].humanTasks`，带落点检测 |

**种子的反面判据（2026-08-20，综述大纲步实测拍板）**：种子的答案若**取决于本步进行中的产出**
（如「借哪篇范式做骨架」要看到候选范式卡片才定得了），它属于按需问不属于种子——
开工前点卡片等于盲猜（与「要先看到数据」同一道理）。另：只读想法卡的结论要手动
「◈ 沉淀进任务书」、且只追加草稿末尾，对「定 TASK.md 参数」类问题（答案要织进任务书正文）
是绕路——这类问题给「跟 AI 商量一下」（开场自动带种子）或直接进简报按需问。

**按需问的写法**（简报内，逐字照抄这个结构）：

```
先报数再定 ×××：统计/粗检得到 N，把「N 与你建议的做法」写进 .ccode/help-wanted.md
问用户一句，说明哪些操作依赖答复、哪些无依赖可逆准备可以继续。关键决定未答时暂停受影响操作，不默认批准。
```

三要素缺一不可：**先给数字** → **给建议及影响** → **写明等待边界与可逆准备**。

**反面判据**：如果这个问题的答案取决于某一步的产出，而你把它摆在那一步之前，就是错的。
（事故：数据处理的「缺失值怎么处理 / 分析粒度 / 要不要合表」摆在第 2 步开工前，
而第 1 步「数据登记与检查」的产出正是这些信息。）

**两条路径要对仗标明（v3.90，用户拍板）**：确定 TASK.md 有方式一（决策项点卡片）与方式二
（「跟 AI 商量一下」聊着定）两条并列路径，终点相同。界面上成对标注「方式一 · 点卡片直接定」/
「方式二 · 聊着定」，节点引导句统摄两条路（「点卡片或跟 AI 聊，都进 TASK.md」）；
**没有决策项的步骤不标「方式二」**——方式一不存在时单标方式二只会让人找方式一（R5 同款道理），
此时聊天入口维持单按钮形态，旁边放 TASK.md，不再跟一句旁白。
**对仗也是视觉的（走查追加）**：两条路**同形**——都是默认折叠的一行（▸ 展开才露动作：
方式一展开是卡片、方式二展开是聊天按钮），行首同宽箭头列对齐；「预览/编辑 TASK.md」是看结果
不是第三条路，跟在本行标签后面（与方式一行的「全部用推荐值」同位），不拉到卡片右缘。

## 三、文案规范

沿用 `design-system.md` 的「一个操作最多一句话（≤20 字），说不完的进 `title=`」，
另加三条步骤面板专属：

1. **禁止在界面上写「为什么这么设计」**。那是代码注释与 `architecture.md §10` 的事。
2. **内部术语不外露**：`register` → 添加/移除；`agent 执行` → AI 干活；
   `评审合并` → 你验收；`只读保护` → 聊天时不让 AI 改文件；`定方向` → 先定几件事；
   `种子` → 不出现在界面上。代码标识符可以继续用内部词，两者是映射关系。
   **页名映射（v3.92）**：UI 上 workspaces 页叫「**项目**」（侧栏/页头/⌘1/命令面板/跨页引用统一）；
   「工作区」在 UI 上只指 git worktree 任务工作区对象（新建工作区按钮、工作区卡、归档/恢复等）。
   代码标识符与开发文档继续用 workspaces/工作区页，与 UI 文案是映射关系。
3. **模板预填的占位不是已填值**：`projectSettings` 预填的是
   「综述角度：（领域全景 / 聚焦某个子问题）」这种带括号空答案，
   展示时**必须过滤**（冒号后去掉括号还剩字才算填过），否则挂一串没意义的问号。

## 四、新增模板 / 新增步骤检查清单

照着走一遍，每条都能答「是」才算完成。

**模板级**

- [ ] 贯穿全程的决定是否都进了 `projectSettings`，而不是塞在某一步的 `decisions` 里？
- [ ] 每个步骤的 `role` 是否如实？（人要出场的步骤标成 `ai` 是最容易犯的错）
- [ ] 步骤名是否是学术习惯叫法，而不是自造词？
- [ ] 与相邻模板的产物路径是否对齐？（接壤约定见 `pipeline.md`）
- [ ] `expectedArtifacts` 是否精确到文件/目录，能被产物核验清单检出？

**步骤级**

- [ ] 每个 `decisions` 是否都通过了「开工前就能答」这一关？
- [ ] 每个预置 `discussionSeeds` 是否都通过了「开工前就能聊出结论」这一关？
      （答案取决于本步进行中产出的 → 改简报按需问；答案要织进任务书正文的 → 留给「跟 AI 商量一下」）
- [ ] 需要先看数据的问题，简报里是否写了「先报数 → 给建议及影响 → 写明等待边界与可逆准备」？
- [ ] 有无开工前提？有的话是否会生成独立节点排在 agent 之前？
- [ ] 人工事项的 `target` 落点，是否真的会因为这件事被完成而出现文件？
      （反例：Zotero 导入不进 `papers/`，落点写 `papers/` 的事项永远打不上勾）
- [ ] `optional` 是否标对？（不做也能跑的必须标）
- [ ] 空 `target` 的人工事项是否使用 `manual`；`all` 是否提供总数或清单来源？
- [ ] 输入是否区分必需、可选和任一组，避免把二选一材料写成全部必需？

**验收：把模板跑一遍 `buildStepFlow`，肉眼看节点链**

```
node --experimental-strip-types <<'TS'
import { PIPELINE_TEMPLATES } from "./src/pipeline-presets.ts";
import { buildStepFlow } from "./src/step-flow.ts";
for (const t of PIPELINE_TEMPLATES) {
  console.log(`══ ${t.name}  全局设定 ${t.projectSettings?.length ?? 0} 条`);
  for (const st of t.steps) {
    const f = buildStepFlow({ step: st, states: [], hasDraft: false, runStatus: "pending" });
    console.log(`  ${(st.role ?? "ai").padEnd(4)} ${st.name.padEnd(12)} ` +
      f.nodes.filter(n => n.section === "main").map(n => n.kind).join(" → "));
  }
}
TS
```

看两件事：**角色是否交替出现**（全是 `ai` 说明角色标错了）、
**节点链是否有空节点**（只有 discuss → agent → review 而 discuss 里没内容）。

## 五、已定论、不要推翻

- **不加 `enabled` 式的开工门控**：注入模式下没有「全局激活态」，门控会与「直接聊」的丝滑路径冲突。
- **上一步收尾软门不算门控（2026-08-20，用户拍板）**：开工确认弹层检测到**紧邻上一步的非可选
  after 事项未勾**时，「确认开始」需按两次（首击知情、按钮变「仍要开工」再击才开）——只确认不阻断，
  与 R6 不冲突。针对的是「上一步没审就开下一步、返工互相拖累」（综述大纲没审就开初稿为首发场景：
  该步「审阅 outline.md 再开初稿」同步转非可选）。机制是通用的（`closingHumanTasks` 口径跨步骤读），
  不给单步骤打补丁。
- **决策项不删**：它的价值在「模板预先想好了该问什么」+「答案能进草稿与 TASK.md」，
  只是不该挡路（折叠 + 可跳过即可）。
- **不做第二个导入入口**：导入动作全局只在「文献与数据」一处；流程线只负责选来源 + 指路。
- **`role` / `settings` 是中性字段**：引擎不认识「检索」「综述」，只做透传与展示（科研语义进模板不进引擎）。
- **放宽检测口径必须绑定具体事项**：事项删了，为它加的口径要一起收回，
  否则会变成无条件强制打勾（事故：`lit_library_hit` 活得比它服务的事项久）。

## 人工依据决策（2026-09-07）

非空问题且 `options=[]` 表示填写证据/批准版本，流程线上保留问题与「写一句…」，不当空节点删掉。编辑器不丢此类条目；没有推荐选项就不出现「全部用推荐值」。状态只说明回答存在，不能宣称验过依据真实性。仍只有一个主 CTA，不增加第二条执行入口。界面用人话（「可以写 / 只准备」），落盘仍用闭集原词。

## 决策摘要与报告入口（2026-09-08）

在人填写关键依据前，Agent 在原报告给出方案、推荐证据、代价/不确定性与等待边界；人选/改/补证据，禁止把“请批准”当方案。现有报告预览承载五项验收摘要，不加另一份报告或仪表盘。固定条数只可作例子，不以空洞批判和凑篇数增加认知负担。保留已有 `decisions.q` 键，避免旧草稿答案因改文案失联。

## 摘要与决定的界面位置（2026-09-08）

开工确认在输入后读真实上游摘要并提供答案输入框；不加新的执行入口，不自动采纳推荐。评审在基础检查后展示本步摘要/未决项，限高滚动保留diff主区；原文纯文本、来源可追溯、状态标报告自述。复现是次级运行操作，完整命令需确认，使用原脚本终端，不复制一套执行器。摘要标题未匹配时给原报告入口，不能假装不存在问题。
